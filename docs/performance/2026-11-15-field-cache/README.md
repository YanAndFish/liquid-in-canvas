# 混合光路的折射场缓存与运动时查表

2026-11-15，Chrome 157.0.8103.39，Apple M1（Metal 3）。生产构建，基线 `52d3c69`（[混合光路的记录](../2026-11-14-hybrid-optics/README.md)），`?gpu&adaptive=0`，桌面视口 1563 × 1013 @2。GPU 时间是整帧跨度，每项两轮，四种配置在每一轮里交替测量。

同一块 GPU 上另有两个会话在测量，各开着一个 Chrome。并发时测到的时间会慢 2–3 倍，所以全部测量按共享笔记里的约定串行进行：测量前取锁，测完立刻释放，并把测量页导航到 `about:blank`。下表里 `profile` 的数字与昨天的记录一致（2.6 / 3.5 / 2.4 ms），可以直接对比。

## 做了什么

- **缓存折射场，不缓存颜色**：混合光路里融合的组（以及被裁剪切开的玻璃）几何静止满 120 ms 后，求交一次，把每个求交档像素的量写进三张纹理：三条光路的落点、入射法线、各条光路的有效程度、入射点高度。之后改用读缓存的管线：每帧读回这些量，按入射点重新算一次外观的平滑合并权重，再照常取样背景与模糊。背景与视频每帧更新；染色、压暗、淡入淡出都不在缓存里。
- **按组的局部坐标存放**：缓存相对组内第一名成员定位，整组平移（随页面滚动）不失效。裁剪边离玻璃足够远时不算几何的一部分，玻璃在裁剪容器里滚动仍然命中。
- **失效条件**：成员的相对位置、尺寸、圆角、厚度、截面参数、按压、材质化、切进玻璃的裁剪边位置、色散、成员数量、着色倍率，任意一项变化（容差 0.01 像素）。
- **运动时查表**：缓存失效的组改用剖面管线，上一次的求交结果在 80 ms 里淡出；重新静止 120 ms 后求交，结果在 160 ms 里淡入。淡化是与二维合并的查表结果按比例混合。等待与淡化期间舞台继续请求重绘，约 0.3 秒。
- **显存**：缓存只覆盖可能落在求交档的范围：两名成员都在“平滑合并范围 + 横向位移”之内的地方，以及裁剪边切进玻璃的一条。纹素与着色像素对齐，每个纹素 32 字节：绿色光路的偏移与法线用 `rgba32float`；红蓝两条光路相对绿色的差、有效程度与高度用 `rgba16float`。
  - 全部缓存的上限是 150 万纹素（48 MB）。超过时先释放最久没有出现的组；单独一组就超过上限时不缓存，静止后每帧逐步求交。
  - 连续 180 帧没有出现的组释放纹理，条目最多 12 个。
  - 实测调参面板与入口按钮的连接处是 480 × 480 纹素，约 7.4 MB。
- **开关**：`fieldCache` 选项与 `stage.setFieldCache()`，缺省打开；测量页用 `?cache=0` 关闭，关闭后与基线逐像素相同。

## 每帧 GPU 时间（毫秒，均值 / P95）

| 场景 | `profile` | `hybrid` 缓存 | `hybrid` 无缓存 | 基线 `hybrid` |
| --- | --- | --- | --- | --- |
| 桌面 @2 滚动 | 2.6 / 3.3 | 2.7 / 3.3 | 3.9 / 7.7 | 3.9 / 7.6 |
| 调参面板展开后滚动（`OPEN_PANEL=1`） | 3.5 / 4.5 | 3.8 / 4.8 | 5.7 / 10.1 | 5.7 / 10.0 |
| 停在 600（顶栏与下方玻璃融合），视频播放 | 2.4 / 3.0 | 2.8 / 3.3–4.2 | 4.4 / 4.7–5.0 | 4.5 / 4.7–5.0 |
| 停在 1100，每 0.9 秒开合调参面板 | 3.3 / 4.1–4.5 | 3.3 / 4.1–4.2 | 5.2 / 7.0–7.1 | 5.2 / 6.7–7.6 |
| 停在 330，每 0.6 秒切换场景标签（液体迁移） | 2.2 / 2.6 | 2.2 / 2.6 | 2.3 / 2.6–2.7 | 2.4 / 2.6–2.7 |

- 无缓存时与基线相同，重构没有带来开销。
- 表中缓存版的数字测于 `1248f38`。最终提交只改了写入时的坐标算法，复核结果一致：停在 600 播放视频 2.64 / 3.21 ms，面板展开后滚动 3.75 / 4.85 ms。
- **几何不变的连接处命中缓存**：
  - 停在 600 播放视频：4.4 → 2.8 ms，比 `profile` 多 0.2–0.4 ms。多出来的是读回折射场之后的着色：菲涅耳、环境反射、按入射点重算的合并权重，外加三次纹理读取。
  - 面板展开后滚动：面板与入口按钮的组命中，5.7 → 3.8 ms。
- **另外两行接近 `profile` 是因为一直在查表，不是命中**：
  - 滚动时固定的顶栏与滚到它下面的玻璃一直在相对运动，缓存每帧失效。所以滚动中的连接处与 `profile` 一样是近似。
  - 0.9 秒开合一次面板时，液体迁移从来没有停下，缓存一次也没有写入（`bake.mjs` 统计到 0 次）。这一行的绘制间隔 P95 从 26.5 ms 降到 17.4 ms，无缓存时开合面板会掉帧。
- **写入缓存的开销**：每 2.6 秒开合一次面板，每次停下写一次。480 × 480 纹素的 `field` 遍约 2.0 ms，那一帧整帧最大 5.3 ms，仍在一帧之内。
- 液体迁移那一行四种配置相差不到 0.15 ms：那个画面上几乎没有求交的像素。

## 画面

### 静止画面

`sweep.mjs` 的四种光路在同一次持锁里连续截取，与 `raymarch` 相差超过 2 级的像素数（融合组与被裁剪玻璃的范围内）：

| 画面 | `profile` | `hybrid` 缓存 | `hybrid` 无缓存 |
| --- | --- | --- | --- |
| 间距从 −80 到 48 逐步 8 像素（17 个位置） | 54289–204623 | 0–41 | 0–41 |
| 间距 56（不再融合） | 83 | 83 | 83 |
| 裁剪：切两侧、切上沿、切下沿 | 839 / 1196 / 1275 | 17 / 17 / 0 | 17 / 17 / 0 |

- 缓存版与无缓存版逐格相同。两者整幅比较最大差 1 级，只有一个画面有 2 级。
- `shots.mjs` 的检查页：缓存版与无缓存版在缺省、重叠、分层三个画面上最大差 1–2 级。“通透加厚、色散 1”一格有 14 个像素超过 2 级（最大 8 级），来自半精度存放的红蓝光路差值。与 `raymarch` 比，三者的差异数分别是 3990 / 197 / 161，无缓存版是 3976 / 197 / 161。
- `shots.mjs` 的商店页（三种光路在同一次会话里连续截取），与 `raymarch` 相差超过 2 级的像素数：

| 画面 | `hybrid` 缓存 | `hybrid` 无缓存 | 缓存与无缓存之间 |
| --- | --- | --- | --- |
| 桌面滚动 0 / 300 / 600 / 900 / 1100 | 602 / 622 / 131 / 70 / 58 | 602 / 622 / 131 / 70 / 58 | 最大差 2 级，0 个超过 2 级 |
| 桌面滚动 1500 / 1900 / 2300 | 145 / 366 / 261 | 145 / 366 / 261 | 逐像素相同 |
| 桌面面板展开（1100） | 91 | 91 | 最大差 1 级 |
| 手机 @3 滚动 0 / 700 / 1800 | 262 / 192 / 339 | 262 / 189 / 339 | 700 处 3 个像素超过 2 级（最大 8） |
| 手机、玻璃 2 倍着色 0 / 700 | 170 / 138 | 169 / 134 | 700 处 4 个像素超过 2 级（最大 5） |

  玻璃着色倍率低于画布倍率时（最后一行），缓存按离屏目标的倍率写入，同样与无缓存版一致。

开发中遇到的三个问题，都已修正：

1. **偏移不能全用半精度**：三条光路的落点偏移可以有几百像素，半精度在 512 以上只有半个像素的精度。没有模糊的背景上，“通透加厚”一格有 603 个像素、最大 168 级的差异。改成绿色光路用单精度、红蓝两条光路只存相对绿色的差之后，降到 14 个。
2. **附件合计不能超过 32 字节**：三张 `rgba32float` 加一张半精度共 40 字节，超过了 WebGPU 缺省的 `maxColorAttachmentBytesPerSample`（32 字节）。管线校验失败，整幅画面变黑。现在的打包正好 32 字节，有测试检查。`rgba32float` 只能按 `unfilterable-float` 绑定，绑定布局按位记录哪些绑定不可过滤。
3. **求交要在画面的像素坐标下进行**：轮廓上下沿那一圈全内反射的光路对坐标的舍入非常敏感。在缓存的局部坐标下求交，每个画面会多出几十个零星像素（最大 89 级）。现在写入时成员保持视口坐标，片元坐标加上缓存原点的整数像素位置，与画面上对应像素的计算逐位相同；读取时也直接按像素坐标找纹素。

### 滚动停下的切换

`transition.mjs` 逐帧录制商店页：每帧滚动 2 像素，从 560 滚到 600，停 0.7 秒，再滚到 640、停 0.7 秒。每次画布绘制之后截取整幅画面，再用 `transition_diff.py` 与 `raymarch` 在同一滚动位置的画面比较，同时比较静止期间的相邻两帧。录制用的是 `1248f38`，之后的提交只改了写入时的坐标，静止画面只会更接近无缓存版。

| 阶段 | 与 `raymarch` 相差超过 2 级的像素（最大差） | 相邻两帧的变化 |
| --- | --- | --- |
| 滚动中（562–598） | 9.4 万–10.7 万（45–80），与 `profile` 相同 | — |
| 停下后 0–130 ms | 93493（68），仍是查表 | 0 |
| 130–280 ms，淡入 | 9 帧里从 89701 降到 363 | 每帧 4000–7300 个像素，最多 13 级 |
| 之后 | 135（36），与无缓存版相同 | 0 |
| 再停下（640） | 2229 → 81，同样淡入 | 最多 11 级 |

- 无缓存版在滚动中就与 `raymarch` 一致（129–135 个像素）。缓存版滚动时连接处是 `profile` 的近似，停下约 0.13 秒后用 0.15 秒渐变到求交的结果。
- 如果不做淡化，停下时连接处会在一帧之内改变 9.3 万个像素、最多 68 级。淡化后每帧最多变化 13 级，看起来是连接处在停下后轻微“沉”到最终形状。
- 640 处有 215 个像素、99 级的一次跳变，`raymarch` 自己也有，是页面内容本身的变化，与缓存无关。

## 结论

**建议采用，缓存在 `hybrid` 里缺省打开。**

收益：

- 几何静止的连接处（停住的顶栏、展开的面板与入口按钮、视频背景上的融合玻璃）开销降到 `profile` 加 0.2–0.4 ms，画面仍与 `raymarch` 一致。
- 运动中（相对滚动、液体迁移、开合面板）开销与 `profile` 相同，不再因为连接处求交而掉帧。

代价：

- 连接处在运动中是剖面查表的近似，停下后约 0.3 秒才完全变成求交的结果。缺省光路本来就是 `profile`，运动中的画面不比缺省差。需要运动中也精确的场合可以用 `fieldCache: false`。
- 最多 48 MB 显存，实际用量随连接处面积变化，面板连接处约 7.4 MB。
- 写入缓存的那一帧多约 2 ms GPU。

有了缓存，`hybrid` 在这台机器上的开销已经接近 `profile`，可以考虑把它设为缺省光路。但上一份记录里手机 @3 的 `hybrid` P95 已到 9.8 ms，这次没有重测手机视口，也没有在真机上测量，应先补这两项再决定。

- `transition.mjs`：逐帧录制“滚动 → 停下 → 再滚动 → 停下”。`FROM`、`TO`、`STEP`、`HOLD` 调整路径，`ROI` 只截一部分画布。
- `transition_diff.py`：每一帧与对照光路在同一滚动位置的差，以及静止期间相邻两帧的变化。
- `bake.mjs`：按间隔点击，让几何反复变化又停下，从逐遍计时里挑出写入缓存（`field` 遍）的帧。
- 四种配置的画面要在同一次 Chrome 会话里连续截取。不同会话之间整幅会有 1–2 级的漂移，而且冷启动后的第一组截图要丢弃。
