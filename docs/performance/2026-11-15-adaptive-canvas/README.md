# 自适应降级：见效判断与画布倍率一级

2026-11-15，Chrome 157.0.8103.39，Apple M1（Metal 3），5K 外接屏。生产构建，`tests/perf/scroll.html` 暂停视频、八秒往返滚动 2200 像素，自适应开启（缺省）。高分辨率视口用 CDP 模拟，GPU 是同一台机器的，**没有在真机上测量**。每个场景重新加载页面后连续跑几轮，不在轮与轮之间重新加载，观察降级怎样收敛。原始数据见 `final-runs.jsonl`。

## 做了什么

[上一份记录](../2026-11-14-hybrid-optics/README.md#高分辨率下的基线)发现：画布超过约 18 MP 时，瓶颈是浏览器把整页画进画布，光路与玻璃着色倍率的降级全部无效，却仍然一路降到底。现在：

- **每一级都要检验**：基准是触发降级的两个慢窗口中较快的一个，降级后（忽略 10 帧）连续两个窗口都要比基准缩短至少 1 ms 且至少 5%，否则撤回这一级，30 秒内跳过这种手段（再次无效则加倍，最多 240 秒），同一帧里换下一种。见效但仍然偏慢时以检验期间较快的窗口为基准接着降。
- **画布倍率一级**排在光路、玻璃着色倍率之后：每级像素数 ×0.75；间隔超出很多时按 17.5 ms ÷ 当前间隔估计，一级最多减半。下限是新选项 `StageResolution.minPixelRatio`（缺省 1，实际不低于 1 与设备倍率中的较小值；`Infinity` 关闭这一级）。`getMetrics()` 多了 `targetDpr`（降级前的画布倍率）。
- **升回**：观察期从 4 个窗口（约 3 秒）改为 20 秒，期间变慢就直接回到升回前的档位（不重新走阶梯），下次尝试推后一倍。
- 帧很慢时窗口满一秒（且不少于 12 帧）就结束，不必凑满 45 帧；舞台开始绘制或修改分辨率限制后的头 2 秒不采样。
- 调参面板显示画布倍率是否被自动降低（及原来的倍率），可以关闭画布倍率一级。测量页结果多了 `adaptation`（本轮的变化）与 `adaptationLog`（自加载起的全部变化）。

## 画布像素数是瓶颈：2560 × 1440 @3（33 MP），`hybrid`

关闭自适应时这个场景是 33.3–33.9 ms（30 帧），GPU 时间 12–13 ms。

| 加载 | 自加载起的变化（秒：画布倍率 / 玻璃着色倍率 / 光路） | 最终 | 最终几轮的绘制间隔（均值 / P50 / P95） |
| --- | --- | --- | --- |
| 1 | 4.2 光路试 `profile` → 5.6 无效撤回，玻璃试 1.5 → 7.0 无效撤回，画布 3 → 2.12 | 2.12 / 2 / `hybrid`（16.6 MP） | 18.1–18.5 / 17.2–18.1 / 22.4–23.0 ms |
| 2 | 同上至 6.9；13.3 画布 → 1.84；19.4 升回 2.12；22.2 升回失败，回到 1.84 | 1.84 / 1.84 / `hybrid`（12.4 MP） | 16.7 / 16.7 / 17.5–18.1 ms |

- 两次加载都在 7 秒内把画布降到能跑满约 60 帧的档位，光路与玻璃着色倍率各试一次、无效后撤回，最终都没有降低。加载 2 的玻璃倍率 1.84 是因为它不超过画布倍率，不是降级。
- 第一级画布降级按 33 ms 的间隔估计把像素数减半（3 → 2.12），没有逐级重建四五次画布。
- 2.12 时均值 18.1 ms 落在 17.5–19.5 之间，既不升也不降；加载 2 在滚到贵的一段时被判为偏慢、降到 1.84，升回一次失败后停在那里。之后流畅的几轮没有再升回：升回要求连续流畅 8 秒（失败一次后加倍），而测量的每轮只有 8 秒，轮与轮之间页面静止会清零计时，持续滚动时会再试。
- 降级后的头一轮均值偏高（20.7、22 ms），是画布重建、降级检验期间的慢帧。

### 关闭画布倍率一级：`minPixelRatio=Infinity`

同一场景，三次加载：

| 加载 | 自加载起的变化 | 最终 | 绘制间隔均值 |
| --- | --- | --- | --- |
| 1 | 4.1 光路试 `profile` → 5.5 撤回，玻璃试 1.5 → 6.9 撤回；35.8 再试光路 → 38.2 撤回，玻璃试 1.5 → 39.5 撤回 | 3 / 2 / `hybrid` | 33.6–35.4 ms |
| 2 | 同上 | 3 / 2 / `hybrid` | 33.1–33.7 ms |
| 3 | 4.2 光路 → 5.6 撤回，玻璃试 1.5 → 8.0 见效，再试 1.125 → 10.4 见效，再试 1 → 11.7 撤回；36.4 再试光路 → 37.7 撤回 | 3 / 1.125 / `hybrid` | 32.4–32.8 ms |

- 加载 3 把玻璃降到 1.125，稳定后确实快了 1.1 ms（33.6 → 32.5，P95 39.5 → 37.5），过了 1 ms 但不到 5%。这两级的检验正好落在测量点击“开始滚动”的时候：基准窗口是静止页面，检验窗口是滚动中，负载本身变了。只看绘制间隔分不清这种变化，这是剩下的局限。
- 检验的写法前后改过两次，原因都来自这个场景：只比一个窗口时，一次加载里光路与玻璃各被误判一次（实际改善 0.3–0.5 ms），因为 30 帧的窗口按 33.3 / 50 ms 量化，几帧卡顿就让均值偏离一两毫秒；基准取两个窗口的平均时，又误判了一次光路，基准窗口在加载后 0–2 秒（推测是图片解码、字体加载的卡顿抬高了基准，加上 2 秒预热后没有再出现）。改成连续两个窗口、基准取较快的窗口、加载后 2 秒不采样之后，剩下的就是上面这一次。

## 玻璃是瓶颈

| 场景 | 最终 | 绘制间隔 | GPU 时间 |
| --- | --- | --- | --- |
| 桌面 1563 × 1013 @2，`raymarch` | 2 / 2 / `raymarch`，没有变化 | 16.7 ms | 6.1 / 9.5 ms |
| 同上，调参面板展开 | 2 / 2 / `raymarch`，没有变化 | 16.8 ms | 11.6 / 20 ms |
| 5K 2560 × 1440 @2，`raymarch` | 画布 2、玻璃 2 不变，光路在 `raymarch` 与 `profile` 之间切换 | 16.7–18.4 ms | `raymarch` 11–12 ms，`profile` 5.2–5.7 ms |

- 这台机器上桌面 @2 的 `raymarch` 本来就跟得上（包括面板展开），不会触发降级。玻璃成为瓶颈的是 5K @2：只有光路被降为 `profile`，画布倍率和玻璃着色倍率始终没动。
- 光路的切换间隔是 7.1 → 13.3 → 16.1 → 25.2 → 31.0 → 48.5 秒，每次升回失败后推迟一倍。改动前（观察期是 4 个窗口）升回后撑过约 3 秒就算成功，滚到画面里贵的一段又降下来，等待时间被重置为 4 秒，每 4–11 秒来回一次。
- `raymarch` 在 5K @2 上均值 18.4 ms，没有超过 19.5 ms，只在滚到贵的一段时被判为偏慢，所以光路在两者之间来回，玻璃倍率不会被降。

## 没有验证的

- 全部是 CDP 模拟视口，GPU 是同一台 M1；没有在真机（手机、5K 原生全屏、其他 GPU）上测量。
- 画布倍率降级后文字变软的观感没有逐像素比较，只确认了 `metrics` 里的倍率与画布尺寸。
- 没有测量画布倍率切换造成的单帧卡顿时长（快照纹理重建）。
- 测量期间同一台机器上曾有其他会话的 Chrome 在渲染，那段时间的数据（基线慢 2–3 倍）已全部丢弃；表中每批前后的对照（2560 × 1440 @2，无玻璃，关闭自适应）都是 16.7 ms。

## 复测

搭环境同[上一份记录](../2026-11-14-hybrid-optics/README.md#复测)，Chrome 用独立的配置目录与调试端口：

```sh
cd apps/demo
pnpm exec vite build --config tests/perf/vite.config.ts --outDir /tmp/liquid-adaptive-build --emptyOutDir
cp /tmp/liquid-adaptive-build/tests/perf/scroll.html /tmp/liquid-adaptive-build/index.html
pnpm exec vite preview --outDir /tmp/liquid-adaptive-build --host 127.0.0.1 --port 4237
```

- 第一条是对照：应为 16.7 ms。明显更慢说明 GPU 被别的进程占用（`ioreg -r -d 1 -c IOAccelerator | grep 'Device Utilization'`），这时的结果不能用。
- `adapt.mjs` 每轮输出一行：绘制间隔、GPU 时间、结束时的实际倍率与光路，以及这一轮的变化；最后一轮另带自加载起的全部变化。
- 测量页的 `?minPixelRatio=` 设置画布倍率的下限。
